# agentic-sql-analyst

**QueryMind** — a self-correcting agentic Text-to-SQL assistant for enterprise
data analytics. CSE 598 (Agentic AI) capstone — *Vinay Kumar Veeramallu*.

This branch contains the **runnable baseline** plus the evaluation harness that
scores it. The baseline is a deliberately simple single-call script: it takes a
natural-language question, inspects a SQLite schema, asks a model for one SQL
query, executes it read-only, and prints the result.

There is **no retry loop, no reflection, and no UI**. That is intentional — the
baseline is the measurement floor the agentic system will be compared against.

> **Every number in `PROPOSAL.md` is regenerated by `make score`, offline, with no
> API key.** Reference queries live in `eval/questions.yaml`; run traces live in
> `eval/results/`.

## Quick start

```bash
git clone https://github.com/Vinay-K-Veeramallu/agentic-sql-analyst.git
cd agentic-sql-analyst && git checkout baseline

make setup          # venv + pinned dependencies (Python 3.11)
make seed           # build data/analytics.db (deterministic, seed 598)
make verify-data    # confirm md5 d612d894b6250755906a962edf27e7ab
make demo           # run the headline test case offline, no API key
make test           # 79 tests
make score          # regenerate every accuracy and latency figure
```

Without `make`: see the explicit commands in [section 5](#5-run-the-baseline).

## 1. Requirements

- Python **3.11** (pinned in `.python-version`; 3.10 should work, untested)
- No database server — a local SQLite file
- An API key is **optional**: `--provider mock` runs fully offline, and `make score`
  never calls a model

## 4. Build the database

```bash
python scripts/seed_db.py     # or: make seed
```

Fixed seed `598`, so every user gets a byte-identical database
(md5 `d612d894b6250755906a962edf27e7ab`, checked by `make verify-data`).

| Table | Rows | Columns |
| --- | --- | --- |
| `customers` | 20 | `customer_id`, `customer_name`, `region`, `signup_date` |
| `products` | 15 | `product_id`, `product_name`, `category`, `unit_price` |
| `orders` | 300 | `order_id`, `customer_id`, `product_id`, `quantity`, `total_amount`, `order_date` |

`orders` has foreign keys into both other tables, so most questions need a JOIN.
Note that `total_amount` is `quantity * unit_price` and **there is no cost
column** — see the construction disclosure in `PROPOSAL.md` §4.

## 5. Run the baseline

```bash
# Offline, no API key (start here)
python src/baseline.py --input examples/test1.txt --provider mock

# Live, against ASU OpenCode
python src/baseline.py --input examples/test1.txt --provider asu

# Ad-hoc question
python src/baseline.py --query "What is the total revenue by region?" --provider asu

# The evaluation set, one arm, writing a trace the scorer can read
python src/baseline.py --questions --set easy,hard --arm b0 --provider asu \
    --trace eval/results/b0_rerun.jsonl
```

### CLI flags

| Flag | Meaning |
| --- | --- |
| `--query` / `--id` | A single question, with an optional id for the trace |
| `--input` | A file with one question per line |
| `--questions [file]` | Run `eval/questions.yaml` (default) |
| `--set` / `--ids` | Filter the evaluation set: `easy,hard` / `E1,H3` |
| `--arm` | `b0` (frozen floor) or `b1` (may refuse) |

| `--db` / `--max-rows` / `--config` | Override database, row cap, config file |
| `--trace` | Append a JSONL trace record per question |

## 7. How the baseline works

```
[question] -> [PRAGMA introspection -> schema block] -> [ONE chat completion]
           -> [guard: single read-only SELECT/WITH] -> [read-only execution]
           -> [pandas DataFrame -> stdout + human log + JSONL trace]
```

On failure the script logs the error and moves on; it **does not retry**.

### Read-only execution is enforced three ways

The connection is opened `?mode=ro`, so SQLite refuses writes itself. During each
query a statement authorizer permits only read/select/function actions, so DDL,
`ATTACH` and `PRAGMA` are denied by the engine. A progress handler interrupts any
query that exceeds its step or time budget, and rows are streamed with a hard cap
that is *flagged* when hit. The keyword check is only for error messages — see
`docs/adr/0001-read-only-execution-boundary.md`. All three are pinned by tests in
`tests/test_guard.py`.

## 8. Arms

| Arm | Prompt | Role |
| --- | --- | --- |
| `b0` | 6 rules, no permission to refuse | The floor. **Frozen by a byte-level SHA-256 test** (`tests/test_llm.py`) — any edit fails the suite and forces a version bump plus re-measurement, because the committed traces were produced with this exact text. |
| `b1` | `b0` + one sentence permitting `NOT_ANSWERABLE: <field>` | The control arm: how much does one sentence buy, before any architecture is credited? |

## 9. About `--provider mock`

`mock` is a deterministic offline stub that keyword-matches against a small table
of hand-written queries. Its rules were written *from* `examples/queries.txt`, so
**its accuracy is meaningless by construction** and is never reported as a result.
It exists so a grader without credentials can run the pipeline end to end.

## 10. Measured results

Model `muse-glimmer-30b` on the ASU RC gateway, 17 live runs per arm, scored by
`make score`:

| Arm | Execution success | Easy (reference) | Hard (reference) | Unanswerable refused | Ambiguity flagged | Fabrications |
| --- | --- | --- | --- | --- | --- | --- |
| `b0` | 17/17 | 5/5 | 2/5 | 0/6 | 0/4 | **6/6** |
| `b1` | 10/17 (7 refusals) | 5/5 | 3/5 | **6/6** | 0/4 | 0/6 |

Latency for `b0` on the original 10-question set: p50 **17.20s**, mean 29.66s,
max 121.80s, 6/10 over the 15s target. An 11th run repeated a question and
returned in 0.86s against 13.41s for identical SQL — a gateway cache hit, excluded
from the statistics and flagged in the trace.

**Two findings.** The baseline makes no SQL syntax or schema errors at all; its
failures are semantic — it answered "what is the profit margin per category?" with
a table of zeros on a schema with no cost column. And the fix for that did **not**
need an agent: one sentence of permission to refuse (`b1`) took refusal from 0/6
to 6/6 with no easy-set regression, at the cost of one over-refusal. See
`docs/adr/0002-control-arms-before-architecture.md`.

## 11. Known limitations

- No self-correction: a malformed query ends that question.
- No natural-language summary and no charts yet.
- **No ambiguity handling:** both arms score 0/4 — vague questions get one silent
  interpretation.
- `b1` over-refuses: it refused H2, an answerable-but-ambiguous question.
- Small samples: 5–6 items per stratum, single run each. A 2/5 result carries a
  95% Wilson interval of 12–77%, printed with every rate.
- One schema, one dialect, one model. The schema is self-authored and its
  unanswerable region was known in advance.
- Results are printed to `max_rows` (default 50); truncation is flagged, not silent.
- Latency p50 exceeds the 15s target.
- CLI only; no CI pipeline yet.
